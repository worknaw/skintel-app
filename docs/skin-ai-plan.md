# แผนพัฒนา AI สแกนผิว SkinCycle

สถานะ: แผนงานและขอบเขตการทดลอง ยังไม่ใช่ระบบวิเคราะห์จริง

สถานะ backend: มี `skin_scan_consent_versions`, `skin_scan_consents` และ RPC `create_consented_skin_scan` บน Supabase สำหรับบันทึก consent และสร้าง scan แบบ atomic/idempotent แล้ว แต่ยังไม่มี consent version ที่ active และยังไม่มีหน้าจอเรียกใช้ จึงยังสร้าง scan จริงจากแอปไม่ได้ ห้ามเปิด consent version จนกว่าจะมีผู้ประมวลผลและระยะเวลาเก็บที่ยืนยันแล้ว รวมถึง rate limit, การถอน consent/ลบข้อมูล และ flow อัปโหลดที่ทดสอบแล้ว

RPC เป็น SECURITY DEFINER ที่อนุญาตให้ authenticated เรียกโดยตั้งใจ และตรวจ `auth.uid()` ภายใน จึงปรากฏคำเตือน security advisor ต้องทบทวนสิทธิ์และเพิ่มมาตรการป้องกันการเรียกซ้ำ/ใช้งานเกินก่อนเปิดจริง bucket ยังไม่มี policy สำหรับผู้ใช้และไม่รองรับอัปโหลด

## 1. สถานะปัจจุบันและเป้าหมาย

- หน้าสแกนใน `src/features/skin-analysis/ui/scan-flow-screen.tsx` ใช้ภาพตัวอย่างและตัวจับเวลา ไม่มีการเปิดกล้องหรือเรียก AI
- `analysis-screen.tsx` แสดงผลและคะแนนที่กำหนดไว้ในโค้ด ไม่ใช่ผลที่วัดได้จากภาพ
- `scan-services.ts` เป็น interface สำหรับกล้องและ AI ยังไม่มี implementation สำหรับใช้งานจริง
- สวิตช์ความเป็นส่วนตัวที่มีอยู่เป็นการบันทึก preference ไม่ใช่หลักฐานการยินยอมส่งรูปให้ผู้ให้บริการหรือใช้ฝึกโมเดล
- ขอบเขต MVP คือการทดลองสังเกตลักษณะที่มองเห็น เช่น บริเวณที่อาจมีสิวหรือรอยแดง โดยต้องยอมรับได้ว่า AI ตอบว่าไม่สามารถประเมินได้
- ประเภทผิวให้แสดงจากข้อมูลที่ผู้ใช้ระบุเอง ความชุ่มชื้น ความมัน คะแนนสุขภาพผิว และรูขุมขนไม่ให้เป็นค่าที่วัดจากภาพจนกว่าจะมีวิธีวัดอ้างอิงและผลตรวจสอบรองรับ
- ใช้เพื่อการทดลองและคำแนะนำทั่วไป ไม่วินิจฉัยโรค ไม่ระบุชื่อโรค ไม่สั่งยา และไม่รับประกันว่าไม่มีปัญหาผิว

## 2. แผนเป็นลำดับ

### ระยะ A: นิยามและเตรียมการทดลอง

1. กำหนดภาพเป้าหมาย: ใบหน้าจริงหนึ่งคน ภาพตรง ไม่มีฟิลเตอร์ แสงสม่ำเสมอ ไม่มีสิ่งบังผิวบริเวณที่ประเมิน
2. กำหนดผลทดลอง: `visible_acne` และ `visible_redness` โดยแต่ละรายการมี `observation` เป็น `observed`, `not_observed` หรือ `unassessable`; เพิ่ม `reason` เมื่อประเมินไม่ได้ ผลนี้เป็นข้อสังเกตจากภาพ ไม่ใช่การวินิจฉัย
3. ทดลองให้ผู้ประเมิน 2 คนติดป้ายกำกับอย่างอิสระตามคู่มือเดียวกัน และบันทึกความเห็นที่ไม่ตรงกัน ก่อนให้ผู้เชี่ยวชาญตัดสินเมื่อจำเป็น
4. คัดเลือกชุดภาพที่เจ้าของอนุญาตและกำหนดสิทธิ์ใช้งาน ตรวจใบอนุญาตและข้อจำกัดการใช้งานของ dataset ก่อนดาวน์โหลดหรือฝึก
5. เปรียบเทียบ baseline อย่างน้อย 2 แนวทาง: แบบง่ายตามข้อมูลที่ผู้ใช้กรอก และ Vision model สำเร็จรูปที่ตั้งค่า prompt/version คงที่ โดยใช้ชุดทดสอบเดียวกัน
6. คัดเลือก provider/model หลังตรวจต้นทุน การใช้ข้อมูล ระยะเวลาเก็บ ข้อกำหนดการส่งต่อข้อมูล และความเหมาะสมกับงบประมาณจริง ยังไม่ผูกแอปกับ provider ใด

งานวิจัยเกี่ยวกับสิวจากภาพโทรศัพท์แสดงให้เห็นว่าคุณภาพภาพส่งผลต่อความเสถียร และข้อมูลจากสถานที่หรือวิธีถ่ายที่ต่างกันควรใช้ประเมินแยกกัน: https://doi.org/10.1038/s41598-024-84670-z

### ระยะ B: กล้องและข้อมูลส่วนบุคคล

1. เชื่อมกล้องหน้าและจัดการสิทธิ์ กรณีอนุญาต ปฏิเสธ และปฏิเสธถาวร พร้อมยกเลิกได้
2. เริ่มด้วยการถ่ายโดยผู้ใช้ควบคุมเอง; เพิ่มการถ่ายอัตโนมัติเฉพาะเมื่อมี face detection และการประเมินตำแหน่งที่ทดสอบแล้ว
3. ตรวจความพร้อมภาพตามความสามารถที่ implement และทดสอบจริง เช่น ใบหน้าหนึ่งคน แสงและความคม หากตรวจไม่ได้ให้บอกตามจริง ไม่แสดงว่าผ่านทุกข้อ
4. แยก consent สำหรับส่งภาพไปวิเคราะห์ออกจาก consent สำหรับใช้ภาพฝึกโมเดล บันทึกข้อความ เวอร์ชัน เวลา และการถอนความยินยอม
5. ระบุชื่อ provider วัตถุประสงค์ ระยะเวลาเก็บ การลบ และการประมวลผลข้อมูลก่อนใช้งานจริง การลบรูปต้นทางต้องรวมทั้งสำเนาและนโยบายของ provider เท่าที่รองรับ
6. ลดขนาดภาพเท่าที่เหมาะสม ไม่ส่ง metadata ที่ไม่จำเป็น และไม่เก็บภาพ/token/URL ลง log

### ระยะ C: Backend และเชื่อม AI

1. สร้าง scan record ที่ผูกกับ `auth.uid()` และที่เก็บภาพแบบ private พร้อม RLS; ใช้ migration และทดสอบสิทธิ์ข้ามบัญชี
2. สร้าง server endpoint ตรวจ session, ownership, consent, ชนิด/ขนาดไฟล์, rate limit และ idempotency ก่อนเรียก provider
3. จัดสถานะ `created → uploaded → processing → completed` และ `failed`/`cancelled` อย่างชัดเจน; ออกแบบ retry ให้ไม่สร้างผลซ้ำ
4. ใช้ provider adapter แยกจาก logic ของแอป secret อยู่ฝั่ง server เท่านั้น; ตรวจ output กับ schema ที่มี version และปฏิเสธผลไม่ถูกต้อง
5. เก็บ model ID/version, prompt version, เวลาทำงาน และสถานะ โดยไม่เก็บข้อมูลมากเกินจำเป็น
6. แสดงสถานะงานจริง ระหว่างรอใช้สถานะแบบไม่ระบุเปอร์เซ็นต์หาก provider ไม่ส่งความคืบหน้าที่วัดได้; ไม่ใช้ตัวจับเวลาแทนผลจริง
7. เชื่อมหน้าแสดงผลให้รองรับประเมินไม่ได้ ภาพไม่ผ่าน network error timeout retry และผู้ใช้ยกเลิก โดยรักษาหน้าตาเดิมเท่าที่เป็นไปได้

### ระยะ D: ประเมินและพัฒนาโมเดล

1. ก่อนทดลองกำหนดคู่มือ label, เกณฑ์คุณภาพภาพ, กลุ่มประชากร, วิธีคัดภาพ, primary metric และเกณฑ์ผ่านให้เหมาะกับจำนวนตัวอย่าง ไม่ตั้งตัวเลขประสิทธิภาพโดยไม่มีหลักฐาน
2. แบ่ง train/validation/test ตามบุคคล ไม่ให้ภาพของบุคคลเดียวกันข้ามชุด; เก็บ test ไว้จนเลือกโมเดลและตั้งค่าจาก validation เสร็จ
3. รายงานจำนวนภาพและจำนวนบุคคลต่อชุด, class distribution, confusion matrix, precision/recall/F1, ช่วงความไม่แน่นอน และอัตราประเมินไม่ได้
4. ตรวจผลแยกตามสีผิว แสง อุปกรณ์ และกลุ่มที่มีข้อมูลพอ พร้อมระบุข้อจำกัดของกลุ่มตัวอย่างเล็ก; ทดสอบภาพซ้ำของบุคคลเดิม
5. บันทึก feedback ของผู้ใช้แยกจาก label ที่ผู้ประเมินยืนยัน ไม่ถือว่า feedback เป็น ground truth โดยอัตโนมัติ
6. เมื่อมีภาพและ label ที่ได้รับอนุญาตเพียงพอ ทดลอง transfer learning จากโมเดลที่อนุญาตการใช้งาน; เปรียบเทียบกับ baseline บนชุด test เดิมโดยไม่ fine-tune ทับชุด test
7. กำหนด version ของ dataset, code, model และ evaluation; deploy หรือแสดงผลจริงต่อเมื่อผ่านเกณฑ์ที่ตั้งไว้และมีการทบทวนผลโดยผู้เกี่ยวข้อง

## 3. แผนข้อมูลและตัวอย่างสัญญาผลลัพธ์

ข้อมูลสำหรับการทดลองควรมี pseudonymous participant ID, image ID, สิทธิ์การใช้, วันที่ถ่าย, ประเภทอุปกรณ์และสภาพแสงที่จำเป็น, label จากผู้ประเมิน, สถานะคุณภาพภาพ และ dataset version หลีกเลี่ยงชื่อจริงและข้อมูลที่ไม่จำเป็น ภาพใบหน้ายังเป็นข้อมูลระบุตัวตนได้แม้ลบชื่อออกแล้ว

ตัวอย่าง contract สำหรับออกแบบเท่านั้น ไม่ใช่ผลวิเคราะห์จริง:

```json
{
  "schema_version": "1",
  "image_quality": "unassessable",
  "observations": [
    { "type": "visible_acne", "observation": "unassessable", "reason": "image_too_blurry" }
  ],
  "source": "model",
  "model_version": "example"
}
```

ไม่แสดง confidence เป็นเปอร์เซ็นต์แก่ผู้ใช้จนกว่าจะมีการ calibration และตรวจความเชื่อถือได้จริง เก็บประเภทผิวจากแบบสอบถามโดยระบุ source ว่า `self_reported` แยกจากผลภาพ

## 4. สิ่งที่ต้องตัดสินใจก่อนเปิดใช้จริง

- Provider และงบประมาณต่อครั้ง รวมถึงการเก็บและส่งต่อภาพตามข้อตกลงของ provider
- ระยะเวลาเก็บภาพจริง การลบ การถอน consent และช่องทางติดต่อเจ้าของโครงการ
- แหล่งภาพที่มีสิทธิ์ใช้ จำนวนผู้ประเมิน และการทบทวนด้านจริยธรรมของสถาบันหากเกี่ยวข้องกับการศึกษาวิจัยในมนุษย์
- เกณฑ์วัดผลขั้นต่ำหลังเห็นการกระจายของข้อมูล และแนวทางรับมือเมื่อประเมินไม่ได้
- รูปแบบหน้า error/consent/result ที่จำเป็น: ต้องตกลงการเปลี่ยน UI กับเจ้าของโปรเจกต์ก่อน implement ตาม UI lock

## 5. งานถัดไป

สร้างคู่มือ label และ test protocol สำหรับ `visible_acne` / `visible_redness` พร้อมชุดข้อมูลทดสอบที่ได้รับอนุญาต จากนั้นจึงเลือก provider สำหรับ benchmark; ห้ามใช้ภาพผู้ใช้จริงหรือเปิดส่งภาพจนกว่าจะมี consent และเงื่อนไขที่ครบถ้วน
